# Search Capability — Design Proposal

**Date:** 2026-05-09
**Status:** Draft
**Scope:** Search-as-you-type (Suggestions API) — Full Search API design to follow

---

## Summary

This document proposes a search capability for the government customer-facing portal. The solution is designed as a reusable SDK that teams embed into their own Node.js applications, giving each team ownership of their data, index, and deployment.

Two APIs are proposed:

| API | Purpose |
|---|---|
| `/suggestions` | Real-time search-as-you-type — returns suggestions as the user types |
| `/search` | Full search — returns ranked excerpts with links to source pages |

This document covers the **Suggestions API**. The Search API design follows separately.

---

## 1. Background

The portal serves customers and agents who need to find services, rules, and information. Content has already been crawled from government websites and stored as structured documents, each containing a **title**, **section**, and **body content**.

The search capability is built as a **reusable SDK** — a library that teams embed into their own applications. Each team owns their own data, index, and deployment.

---

## 2. How the Suggestions API Works

### 2.1 User Experience

The suggestions API is designed to handle two natural search behaviours:

**Short topic queries** — users who know what they're looking for:
> `renew licence` → `Driver Licence Renewal`, `How do I renew my driver's licence?`

**Natural language questions** — users describing a situation:
> `how do I renew my driver licence?` → `How do I renew my driver's licence?`, `What documents do I need to renew my licence?`

### 2.2 End-to-End Flow

The API has two tiers. **Tier 2 is optional** — teams can enable it if they need maximum coverage, or rely on Tier 1 alone.

**Default (Tier 1 only):**
```
User types in search box
        │
        ▼
  [300ms debounce]
  Wait for pause before firing API call
        │
        ▼
  POST /suggestions?q=<query>
        │
        ▼
  ┌─────────────────────────────────┐
  │  Tier 1: Fast keyword search    │  ~1–50ms
  │  Prefix + fuzzy matching        │
  └─────────────────────────────────┘
        │
        ▼
  Return top suggestions
  [ "How do I renew my driver's licence?",
    "Driver Licence Renewal",
    "What documents do I need for renewal?" ]
```

**Enhanced (Tier 1 + Tier 2 semantic fallback):**
```
  ┌─────────────────────────────────┐
  │  Tier 1: Fast keyword search    │  ~1–50ms
  └─────────────────────────────────┘
        │
        ▼ (only if results < threshold)
  ┌─────────────────────────────────┐
  │  Tier 2: Semantic search        │  ~100–200ms
  │  Vector similarity search       │  (optional)
  └─────────────────────────────────┘
        │
        ▼
  Return top suggestions
```

### 2.3 Why Tier 1 Alone Is Often Sufficient

The suggestions index is not built from raw document text — it is pre-populated with **LLM-generated questions** that already cover the natural language phrasings users are likely to type. This means fuzzy and prefix matching against the index entries is already matching against high-quality, human-readable questions, not raw body text.

For example, the index for a driver licence renewal page already contains entries like:
- `"How do I renew my driver's licence?"`
- `"What documents do I need to renew my licence?"`
- `"How much does it cost to renew my driver's licence?"`

A user typing `"renew licence"` or `"how do I renew"` will match these entries directly via prefix or fuzzy matching — **no vector search needed**.

Semantic search (Tier 2) adds value for edge cases: unusual phrasing, synonyms, or queries that share meaning but share no common words with any index entry. Teams can start with Tier 1 and enable Tier 2 only if they identify coverage gaps in practice.

### 2.3 What the Suggestions Index Contains

The suggestions index contains two types of clean, readable entries:

**Keywords** — extracted from content structure (no AI cost):
- Document titles: `Driver Licence Renewal`
- Section headers: `Required Documents`, `Eligibility Criteria`
- Key terms from body content: `Class 1 licence`, `$45.50 renewal fee`

**Questions** — generated by an AI pipeline (3–5 per content section):
- `How do I renew my driver's licence?`
- `What documents do I need to renew my licence?`
- `Where can I go to renew my licence?`
- `How much does it cost to renew my driver's licence?`

This ensures suggestions are always clean, natural language strings — never raw document excerpts.

### 2.4 Index Schema

| Field | Type | Description |
|---|---|---|
| `id` | string | Unique identifier |
| `text` | string | Display text (question or keyword) |
| `type` | `question` or `keyword` | Used for display and routing |
| `embedding` | vector | For semantic search |

## 3. Backend Options

The SDK supports pluggable backends. Teams choose based on their infrastructure and data size. Three options are recommended; three are evaluated and not recommended for this project.

---

### Option A — MiniSearch *(Recommended: small datasets)*

An in-process JavaScript search library embedded directly inside the SDK. No separate service required.

**How it works:**
- The full suggestions index is loaded into application memory on startup
- Fuzzy and prefix matching runs in-process (~1–5ms)
- Semantic fallback via Azure AI Search is available but optional

**Default flow (keyword only):**
```
Query → MiniSearch (in-memory fuzzy + prefix)
```

**Enhanced flow (with optional semantic fallback):**
```
Query → MiniSearch (in-memory fuzzy) → [optional fallback] → Azure AI Search (vector)
```

| Attribute | Detail |
|---|---|
| **Latency** | ~1–5ms (keyword), ~150–200ms (if semantic fallback enabled) |
| **Monthly cost** | Free (keyword only). Azure AI Search cost applies if semantic fallback enabled |
| **Infrastructure** | None — part of the SDK |
| **Maintenance** | None |
| **Data sovereignty** | Full — data stays in-process |
| **Semantic search** | Optional — via Azure AI Search fallback |
| **Best for** | Teams with small datasets (<5,000 items) or no existing infrastructure |

**Limitations:**
- Semantic search requires Azure AI Search if enabled
- Each application instance holds its own copy — hot-reload requires restart or scheduled refresh

---

### Option B — RediSearch *(Recommended: medium/large datasets)*

Redis with the Search module (Redis Stack). A self-hosted service shared across all application instances.

**How it works:**
- All instances connect to a shared Redis Stack instance
- Prefix and fuzzy suggestions run natively (~1–10ms)
- Semantic fallback uses vector search within the same Redis instance — no Azure AI Search needed

**Default flow (keyword only):**
```
Query → RediSearch (prefix + fuzzy)
```

**Enhanced flow (with optional semantic fallback):**
```
Query → RediSearch (prefix + fuzzy)
      → [optional fallback] → Azure OpenAI (embedding) → RediSearch (vector)
```

| Attribute | Detail |
|---|---|
| **Latency** | ~1–10ms (keyword), ~60–120ms (if semantic fallback enabled) |
| **Monthly cost** | Free (self-hosted). Azure OpenAI cost applies if semantic fallback enabled |
| **Infrastructure** | Redis Stack deployment required |
| **Maintenance** | Redis upgrades, monitoring, memory management |
| **Data sovereignty** | Full — self-hosted within your infrastructure |
| **Semantic search** | Optional — native vector search within Redis, no Azure AI Search dependency |
| **Multi-instance** | All instances share one index — updates propagate immediately |
| **Best for** | Teams already running Redis, medium-to-large datasets |

**Limitations:**
- Requires Redis Stack (not plain Redis)
- New service to procure and deploy if Redis is not already in the stack

---

### Option C — Azure AI Search *(Recommended: already on Azure)*

Managed search service. Can act as the primary backend or as a semantic fallback for MiniSearch.

**How it works:**
- The Azure AI Search Suggest API handles prefix and fuzzy matching for both questions and keywords (~20–50ms) — covering the vast majority of queries
- Semantic vector search is available as an optional fallback for novel or ambiguous queries

**Default flow (keyword only):**
```
Query → Azure AI Search Suggest API (prefix + fuzzy) ~20–50ms
```

**Enhanced flow (with optional semantic fallback):**
```
Query → Azure AI Search Suggest API (prefix + fuzzy) ~20–50ms
      → [optional fallback: only when results < threshold]
        → Azure OpenAI (embedding) + Azure AI Search vector ~150–200ms
```

| Attribute | Detail |
|---|---|
| **Latency (typical)** | ~20–50ms |
| **Latency (fallback)** | ~150–200ms (optional — only for novel or ambiguous queries) |
| **Monthly cost** | Basic: ~$73/month. Standard S1: ~$219/month. Azure OpenAI cost applies if semantic fallback enabled |
| **Infrastructure** | Already deployed — minimal setup |
| **Maintenance** | Managed service — Microsoft handles infrastructure |
| **Data sovereignty** | Partial — data in Azure, within agreed cloud boundary |
| **Semantic search** | Optional — native vector search |
| **Best for** | Teams already on Azure AI Search |

**Limitations:**
- Higher typical latency than MiniSearch or RediSearch (~20–50ms vs ~1–10ms)
- Ongoing cost even at low usage

---

### Option D — Algolia *(Not Recommended)*

Commercial SaaS search platform.

| Attribute | Detail |
|---|---|
| **Latency** | ~5–10ms globally |
| **Monthly cost** | ~$150–500+ |
| **Data sovereignty** | ⚠ Data sent to Algolia's servers |
| **Best for** | Non-government, public-facing portals only |

**Why not recommended:**
- **Data sovereignty is a likely hard blocker** — citizen query data is sent to a third-party SaaS with no self-hosting option
- Requires DPA, security review, and vendor assessment
- Semantic search is a premium add-on, not native

---

### Option E — Typesense *(Not Recommended)*

Self-hosted, open-source search engine.

| Attribute | Detail |
|---|---|
| **Latency** | ~1–5ms (keyword), ~100–150ms (semantic) |
| **Monthly cost** | Free (self-hosted) |
| **Data sovereignty** | Full |

**Why not recommended:**
- Net-new service with no existing presence in the stack — no advantage over RediSearch or Azure AI Search already available
- High-availability clustering is non-trivial on Cloud Foundry
- Embedding generation still requires Azure OpenAI — same as all other options

---

### Option F — Meilisearch *(Not Recommended)*

Self-hosted, open-source search engine.

| Attribute | Detail |
|---|---|
| **Latency** | ~1–10ms (keyword), ~100–200ms (semantic) |
| **Monthly cost** | Free (self-hosted) |
| **Data sovereignty** | Full |

**Why not recommended:**
- Single-node only — no native clustering for high availability
- Vector and hybrid search features are still maturing
- Net-new service with no advantage over existing options in the stack

## 5. Recommended Configuration Per Team Scenario

Options A, B, and C are recommended. Options D, E, and F are not recommended for this project.

All recommended backends support keyword-only mode by default. Semantic fallback can be enabled per team as needed.

| Team scenario | Recommended backend | Semantic fallback |
|---|---|---|
| Small dataset, no Redis | MiniSearch | Optional — enable Azure AI Search fallback if coverage gaps identified |
| Medium/large dataset, has Redis Stack | RediSearch | Optional — enable Redis KNN fallback if coverage gaps identified |
| Already on Azure AI Search only | Azure AI Search | Optional — enable vector fallback if coverage gaps identified |
| Non-government, public data | Algolia | N/A — only if data sovereignty is not a constraint |

## 6. SDK Configuration

Teams configure the suggestions backend via SDK config. The backend, fallback behaviour, and Azure credentials are all configurable per deployment:

Semantic fallback is **disabled by default**. Teams opt in explicitly once they have identified coverage gaps in practice.

```typescript
const sdk = createSearchSDK({
  suggestions: {
    backend: 'minisearch',           // 'minisearch' | 'redisearch' | 'azure'
    semanticFallback: false,         // default: false — enable only if keyword search coverage is insufficient
    fallbackThreshold: 3,            // min results before falling back (only relevant if semanticFallback: true)
  },
  azure: {
    searchEndpoint: process.env.AZURE_SEARCH_ENDPOINT,
    searchApiKey: process.env.AZURE_SEARCH_API_KEY,
    openAiEndpoint: process.env.AZURE_OPENAI_ENDPOINT,   // only needed if semanticFallback: true
    openAiApiKey: process.env.AZURE_OPENAI_API_KEY,
  },
})
```

> **Why this default makes sense:** The suggestions index is pre-populated with LLM-generated natural language questions. Fuzzy and prefix matching against these high-quality entries covers the vast majority of user queries without needing vector search. Semantic fallback is an optional enhancement — not a requirement.

## 7. Questions for Product Owners

The following questions need answers before finalising the approach for each team.

| # | Question | Why it matters |
|---|---|---|
| 1 | What is the expected volume of content per team? (number of documents/pages) | Determines whether MiniSearch is viable or whether a shared service (RediSearch, Azure) is needed |
| 2 | How frequently is the content updated? | Drives the index refresh strategy — real-time vs. scheduled pipeline |
| 3 | What is the acceptable lag between a content change and it becoming searchable? | Affects whether hot-reload or restart-based refresh is acceptable |
| 4 | Is Redis Stack already provisioned in the infrastructure stack for any teams? | Determines whether RediSearch is a zero-procurement option |
| 5 | Is there an existing Azure AI Search subscription available for the portal? | Determines whether Option C is zero-cost to adopt |
| 6 | What are the data retention requirements for search queries? Can queries be stored for analytics or improvement purposes? | Affects logging strategy and vendor eligibility |
| 7 | What is the expected concurrent user load during peak periods? | Informs scaling and infrastructure sizing |
| 8 | Will multiple teams share a single search index, or does each team need an isolated index? | Affects indexing pipeline design and cost model |
| 9 | Are there multilingual or accessibility requirements? (e.g., te reo Māori content) | May affect tokenisation, fuzzy matching behaviour, and question generation prompts |
| 10 | Which teams will be the first adopters, and what is the target go-live timeline? | Needed to prioritise backend option and plan delivery |

## 9. Glossary

| Term | Meaning |
|---|---|
| **BM25** | Best Match 25 — algorithm for keyword relevance scoring |
| **Vector search** | Search by meaning using numerical embeddings — finds semantically similar content |
| **Hybrid search** | Combining keyword (BM25) and vector search in one query |
| **Embedding** | A numerical representation of text generated by an AI model, used for semantic comparison |
| **KNN** | K-Nearest Neighbours — finds the K most similar vectors in an index |
| **Debounce** | Delay before firing an API call — prevents a request on every single keystroke |
| **Suggester** | Azure AI Search feature optimised for prefix-based typeahead |
| **FT.SUGGET** | RediSearch command for autocomplete/typeahead suggestions |
| **Chunking** | Splitting large documents into smaller pieces for more precise search results |
| **SDK** | Software Development Kit — a library that teams embed into their own applications |
