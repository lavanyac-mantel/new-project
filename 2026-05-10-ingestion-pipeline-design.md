# Ingestion Pipeline — Design Proposal

**Date:** 2026-05-10
**Status:** Draft
**Scope:** Python pipeline for processing government content into the suggestions index

---

## Summary

This document describes the pipeline that processes government content into the search suggestions index. The pipeline is responsible for transforming raw markdown files into clean, searchable entries — keywords and questions — that power the suggestions API.

---

## 1. Background

The suggestions index does not contain raw document text. It contains two types of clean, natural language entries:

- **Keywords** — readable phrases extracted from content structure (titles, section headers, key terms)
- **Questions** — natural language questions generated by AI that a member of the public might type to find the content

This approach ensures the search index is always clean and human-readable, and that suggestions feel natural rather than like raw document excerpts.

---

## 2. Pipeline Overview

```
Government Markdown Files (title + section + body)
        │
        ▼
    [Section Chunker]
    Split each document into sections
    Each chunk carries: title + section header + body
        │
        ├──► Keyword Extraction
        │    ├── Structural (always)        → titles + section headers
        │    ├── Option A: Azure AI Language → key phrases from body text
        │    └── Option B: AI prompt        → keywords generated alongside questions
        │
        └──► Question Generation
             Azure OpenAI — using full context (title + section + body)
             → 3–5 questions per section
        │
        ▼
    [Embedding Generation]
    Azure OpenAI — generates a vector for every keyword and question
        │
        ▼
    Search Index
    { id, text, type, embedding }
```

## 3. Chunking Strategy

### 3.1 Approach — Section-Based Chunking

Each document is split into sections using its structural headers. Every chunk carries three fields passed to the AI:

| Field | Content |
|---|---|
| Title | Document title |
| Section | Section header |
| Body | Body text under that section |

**Why section-based rather than fixed block sizes:**
- Government documents already have semantic structure — headers divide distinct topics
- Questions generated per section stay focused and avoid blending unrelated content
- Avoids mid-sentence splits that reduce question quality

### 3.2 Chunk Size Limits

If a section body is very long, it is split into sub-chunks with overlap. The title and section header are carried forward into every sub-chunk to preserve context.

| Parameter | Value |
|---|---|
| Max chunk size | ~400 tokens (~300 words) |
| Overlap | ~50 tokens — for continuity across sub-chunk boundaries |

### 3.3 Why Context Carry-Forward Matters

Every chunk passed to AI includes the full title and section header — not just the body text in isolation. Without this context, generated questions are too generic to be useful.

**Without context:**
> Body: *"You will need to bring your passport and proof of address"*
> Generated question: *"What do I need to bring?"* — too vague

**With title + section context:**
> Title: *Driver Licence Renewal* / Section: *Required Documents*
> Generated question: *"What documents do I need to renew my driver's licence?"* — correct and searchable

## 4. Keyword Extraction

Keywords are clean, readable phrases that serve as fast-match targets in the search index.

### 4.1 Structural Extraction *(always runs — no AI cost)*

Extracted directly from document structure — no AI required:

- Document titles
- Section headers (H2, H3)

These are always included regardless of which body keyword option is chosen.

### 4.2 Body Keyword Extraction *(optional)*

Section body text may contain important terms not captured by headers — policy codes, fee amounts, eligibility criteria, named processes (e.g. *"Class 1 licence"*, *"$45.50 renewal fee"*). Two options are available:

---

#### Option A — Azure AI Language

A dedicated Azure Cognitive Service that extracts key phrases from body text.

| Attribute | Detail |
|---|---|
| **Cost** | Per-document pricing via Azure AI Language |
| **Quality** | Good for noun phrases; may occasionally produce noisy fragments |
| **Infrastructure** | Requires Azure AI Language service |
| **Coupling** | Independent of question generation |

---

#### Option B — AI Prompt (Combined Call)

Keywords are extracted as part of the same AI call as question generation — no additional service required.

| Attribute | Detail |
|---|---|
| **Cost** | No additional API call — reuses the question generation call |
| **Quality** | High — context-aware, AI understands what terms are search-worthy |
| **Infrastructure** | Azure OpenAI only — no extra service |
| **Coupling** | Keywords and questions generated together — simpler operationally |

---

#### Option Comparison

| | Option A — Azure AI Language | Option B — AI Prompt |
|---|---|---|
| **Extra API call** | Yes | No |
| **Extra service** | Yes | No |
| **Keyword quality** | Good (noun phrases) | High (context-aware) |
| **Noise risk** | Medium | Low |
| **Operational complexity** | Higher | Lower |
| **Best for** | Teams already using Azure AI Language | Teams wanting minimal services |

---

## 5. Question Generation

Questions are generated by Azure OpenAI using the full section context (title + section + body). The AI is instructed to generate questions in natural, conversational language — the kind of phrasing a member of the public would actually type.

### Parameters

| Parameter | Value | Reasoning |
|---|---|---|
| Model | GPT-4o | Best instruction-following for structured output |
| Temperature | 0.3 | Low variance — consistent, factual output for government content |
| Questions per section | 3–5 | Covers distinct angles without redundancy |

### Quality Filters

Applied after generation, before indexing:

- Discard questions that are too short to be meaningful
- Discard any output that is not phrased as a question
- Deduplicate — re-running the pipeline does not create duplicate index entries

---

## 6. Embedding Generation

Every keyword and question is converted into a vector embedding using Azure OpenAI. Embeddings enable the semantic fallback tier — allowing the API to find relevant suggestions even when the user's phrasing doesn't exactly match any keyword or question.

| Parameter | Value |
|---|---|
| Model | text-embedding-3-small |
| Input | The text of each keyword or question |
| Output | A numerical vector stored alongside the entry |

---

## 7. Search Index Schema

| Field | Type | Description |
|---|---|---|
| `id` | string | Stable unique identifier — consistent across pipeline re-runs |
| `text` | string | Display text shown to the user (question or keyword) |
| `type` | `question` or `keyword` | Used for display and search routing |
| `embedding` | vector | Enables semantic similarity search |

---

## 8. What the Pipeline Produces Per Section

| Source | Entry type | AI cost |
|---|---|---|
| Document title | Keyword | None |
| Section headers | Keyword | None |
| Body key phrases | Keyword | Option B only |
| Generated questions | Question | Yes — Azure OpenAI |

---

## 9. Operational Considerations

| Concern | Approach |
|---|---|
| **Content updates** | Pipeline tracks which sections have changed — only re-processes updated content |
| **Deduplication** | Entries are identified by a hash of their text — re-runs upsert rather than duplicate |
| **Cost control** | Structural keywords are free; AI cost is per-section for question generation and (optionally) body keywords |
| **Failure handling** | Failed sections are logged and skipped — the pipeline does not abort on a single failure |
| **Throughput** | Concurrent AI calls are capped to stay within Azure OpenAI rate limits |

## 10. Questions for Product Owners

| # | Question | Why it matters |
|---|---|---|
| 1 | How frequently is the source content updated? | Determines whether the pipeline runs on a schedule, on-demand, or triggered by content changes |
| 2 | What is the acceptable lag between a content update and it becoming searchable? | Affects pipeline trigger design — near-real-time vs. nightly batch |
| 3 | Who is responsible for running and monitoring the pipeline? A central platform team, or each content team independently? | Affects pipeline ownership, alerting, and support model |
| 4 | Should generated questions go through a human review step before going live in the search index? | If yes, a review/approval workflow needs to be designed |
| 5 | Is there an existing Azure OpenAI deployment that can be used, or does one need to be provisioned? | Affects procurement timeline and cost baseline |
| 6 | What is the expected content volume? How many documents and sections are in scope? | Needed to estimate AI running costs and index sizing |
| 7 | Are there content categories that should be excluded from question generation or search? (e.g. internal-only pages, archived content) | Affects pipeline filtering logic |
| 8 | Who owns the quality of generated questions long-term? Is there a feedback mechanism to improve them over time? | Affects whether a quality review loop or fine-tuning strategy is needed |
| 9 | Is Azure AI Language already provisioned for any teams? | Determines whether Option A for body keyword extraction is zero-procurement |
